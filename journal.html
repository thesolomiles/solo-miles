2026-08-24 · Sunday

  • Mobile black-blob bug. Leonard reported thesolomiles.com on an iPhone showing large pure-black blobs over the buildings/car (garage interior + parked car rendered as a solid black silhouette), while the lit-window glow band rendered fine. Confirmed via the in-app browser that the scene renders correctly on a normal (host) GPU — so it's an iOS-Safari-GPU-specific rendering failure, not a logic bug, and it's localized to enclosed/shadowed geometry (not full-screen).
  • Root cause: two iOS-hostile effects. (1) THREE.VSMShadowMap (set on the <Canvas shadows>) — VSM's shadow map is a half-float target that iOS filters unreliably, and its blur pass smears the failure into soft black clouds over anything in shadow. (2) N8AO with halfRes in the PostFX stack — the half-resolution depth reconstruction misfires on mobile GPUs and paints enclosed geometry black. Both match the symptom exactly.
  • Fix: a mobile render path (systems/device.ts → IS_MOBILE, keyed off matchMedia('(pointer: coarse)'), the same signal the touch HUD uses). On mobile only: shadows fall back to the robust PCFSoftShadowMap (App.tsx) and the N8AO pass is skipped (PostFX.tsx, rebuilt as a filtered effects array since EffectComposer's children type rejects false). Desktop is byte-for-byte unchanged — still VSM + full N8AO grade. Shadows still ground the scene on mobile, so the diorama look survives.
  • Verified: pnpm build clean (only the known three.js bundle-size advisory); desktop scene re-checked in-browser (house/café glow, player shadow, AO, no black blobs). The true confirmation is on Leonard's iPhone once shipped — the in-app browser can't reproduce the iOS GPU quirk (same host GPU either way).
  • Deployed — didn't fix it. Shipped (d4d157d4) and Leonard re-tested on iPhone: blobs persist, plus new black speckle acne on the ground (PCF's tighter bias needs). Confirmed the live bundle hash matched the new build, so he was running the new code. Two deductions: (1) N8AO is NOT the cause — it's already off on mobile in this build and the blobs remain; (2) shadows-alone can't explain it either — the café front face is fill-lit on desktop, and a shadow map only subtracts the key-sun term, so it can't turn a fill-lit face black. Leaning toward the secondary lights (fill/hemisphere) or a specific material failing on iOS.
  • Shipped an on-device diagnostic build (systems/diag.ts, ?d= param) to bisect the failing layer in a few taps on the real phone (the in-app browser can't repro the iOS fault). Flags: ?d=unlit (every mesh → MeshBasicMaterial, albedo/texture only, no lights/shadow/post — isolates geometry/texture from the lighting pipeline), ?d=noshadow (shadows off), ?d=nopost (composer off). Wired into App.tsx (shadows), PostFX.tsx (early return null), TownModel.tsx (material swap). To remove once the cause is pinned.
  • NAILED IT — it's the post-processing composer, not shadows or AO. Leonard's on-device bisect (also confirmed in a fresh incognito Chrome, so not a cache artifact; Chrome-iOS uses the same WebKit engine as Safari): ?d=nopost → CLEAN, ?d=unlit → CLEAN, ?d=noshadow → still black. The blobs die exactly when post is off. Root cause: Bloom's mipmapBlur needs linear filtering of the composer's HDR (half-float) render target, which iOS WebKit does unreliably — NaNs propagate through the blur and paint pure-black blobs around the brightest emissive spots (window glass, headlights), with the tell-tale soft/cloud-like edges. Shadows (VSM) and materials render fine on iOS.
  • Fix: run the post composer in LDR on mobile. Set EffectComposer frameBufferType={IS_MOBILE ? THREE.UnsignedByteType : THREE.HalfFloatType} (PostFX.tsx) — an 8-bit buffer filters reliably on iOS, so Bloom still glows with no NaN and no blobs. Desktop keeps the half-float buffer for full bloom range. Also reverted the PCF shadow switch back to VSM everywhere (PCF was never the cause and its bias introduced ground-acne speckles), and kept N8AO off on mobile (it's another half-float pass iOS filters unreliably, plus a perf win). pnpm build clean; desktop re-verified unchanged. ?d= diagnostics left in for this deploy to confirm on-device, then to be removed.
  • LDR fix deployed but no change on device — and the live bundle hash matched, so Leonard was running it. Prime suspect: IS_MOBILE (coarse-pointer only) was evaluating false on iPhone Chrome, so none of the mobile-gated branches (LDR buffer, N8AO-off, and earlier the PCF/shadow ones) ever applied — which also explains why every prior "mobile" deploy looked identical. Hardened detectMobile() (coarse pointer or maxTouchPoints>0/ontouchstart or iphone/ipad/android/mobile UA) and added more diagnostics to remove the guesswork: ?d=info (on-screen readout of IS_MOBILE / pointer / touch / UA), ?d=ldr (force the LDR buffer regardless of device), ?d=nobloom (drop only the Bloom pass). Pending Leonard's re-test of the plain URL + ?d=info.

With hardened detection, ?d=info on-device confirmed IS_MOBILE=true / pointer:coarse=true / maxTouchPoints=5 (iPhone Chrome, iOS 26) — so the mobile path (LDR buffer, N8AO off) was running, and still black. Then ?d=nobloom was also still black. So it's not Bloom and not the buffer format (verified frameBufferType is honored by the lib and the LDR buffer applied). The one clean case remained ?d=nopost — i.e. iOS WebKit corrupts this scene the moment it's routed through the EffectComposer's offscreen render target (pure-black blobs around the bright emissive spots), independent of which passes run.
